# Vue-фронтенд магазина — этапы F1–F10

Работает каталог FastAPI: загрузка, ошибка с повтором, пустой список, карточки
с ценой и доступными размерами. Этап F2 добавляет поиск по названию, бренд,
размер в наличии, диапазон цены, сброс и пагинацию (3/12/24 товара на странице).
Этап F3 добавляет регистрацию, вход, профиль и выход. В F4 доступны выбор
размера, добавление и просмотр корзины. F5 добавляет изменение количества
и удаление позиций. F6 добавляет оформление заказа из корзины,
F7 — историю заказов и просмотр отдельного заказа. F8 добавляет снимки
названия товара и размера в позиции новых заказов. F9 добавляет управление
товарами для администратора. F10 добавляет размеры и склад.

## Запуск

Нужны Node.js `^20.19.0 || >=22.12.0` и запущенный бэкенд на `127.0.0.1:8000`
(инструкция: [backend README](../presentation/sneaker-practice/README.md)).
Из корня репозитория:

```sh
cd frontend
npm ci
npm run dev
```

Откройте http://127.0.0.1:4200. Каталог публичный, учётная запись не нужна. Регистрация: `/register`,
вход: `/login`, профиль: `/account`, корзина: `/cart`.
`strictPort` не позволяет Vite молча переключиться на другой порт, если 4200 занят.

Браузер вызывает `/api/products?limit=13&offset=0` на порту 4200: это первая
страница из 12 товаров плюс одна запись для проверки следующей страницы. Vite удаляет
префикс `/api` и передаёт запрос бэкенду на порт 8000. Это аналог `proxy.conf.json`
в Angular; CORS менять не требуется. Этот прокси работает только у dev-сервера.
Для будущего развёртывания потребуется аналогичный маршрут `/api` на веб-сервере.

```text
src/stores/auth/auth.store.ts            общая сессия Pinia, восстановление и выход

src/api/cart.api.ts                 чтение корзины и добавление позиции

src/api/http.client.ts               JSON-запросы, таймаут, JWT и тип ошибки ApiError
src/api/auth.api.ts               register/login/getProfile и типы
src/views/AuthView/AuthView.vue        форма входа/регистрации
src/views/AccountView/AccountView.vue     профиль из API и его обновление
src/views/CatalogView/CatalogView.vue     страница: применённые фильтры, загрузка, пагинация
src/components/catalog/CatalogFilters/CatalogFilters.vue форма: черновик полей, валидация, событие apply

src/styles.css                тема, базовые правила, общие элементы и утилиты
vite.config.ts                сборка, порт и dev-прокси
```

`<script setup lang="ts">` — логика компонента, `<template>` — его HTML.
`ref` хранит реактивное состояние: в TypeScript оно меняется через `.value`,
в шаблоне Vue раскрывает его автоматически. `computed` пересчитывается при
изменении зависимостей. `onMounted` запускает загрузку после появления страницы.
`v-if` выбирает состояние интерфейса, `v-for` выводит список; `:key` идентифицирует
элементы. `defineProps` задаёт входные параметры карточки, как Angular inputs.

API-функция использует встроенный `fetch`, а не отдельную HTTP-библиотеку.
Она проверяет HTTP-статус: `fetch` сам не считает 4xx/5xx исключением.
Интерфейс TypeScript описывает ожидаемый JSON, но не валидирует его в runtime.
Цена и размер приходят строками, как Decimal в Swagger. Перевод цены в Number
здесь нужен только для отображения: расчёт заказа остаётся на сервере.

Pinia хранит общую сессию пользователя, которую используют шапка и страницы.
Состояние каталога остаётся локальным, корзина хранится в отдельном cart.store.
Демо-счётчик генератора удалён.
Фото не выдумываются: при отсутствии картинки или ошибке загрузки показана заглушка.

## F2: как работают фильтры и пагинация

`CatalogFilters.vue` хранит черновик через `reactive`. `v-model` связывает поля
с объектом формы (аналог двусторонней привязки Angular). Для `type="number"`
Vue автоматически приводит ввод к числу, но очищенное поле остаётся пустой
строкой, поэтому тип поля — `number | ''`. Нулевую цену нельзя отбрасывать
проверкой `if (value)`: 0 — допустимый фильтр.

`@submit.prevent` вызывает обработчик без перезагрузки страницы. HTML проверяет
минимум, максимум и шаг числовых полей, а обработчик отдельно проверяет
`minPrice <= maxPrice`. `defineEmits` описывает событие `apply`: через него
форма передаёт странице готовые параметры, аналог `@Output` в Angular.
Новые фильтры и сброс сразу запрашивают первую страницу. Кнопка обновления
и пагинация используют применённые параметры, даже если черновик уже изменён.

`URLSearchParams` в API-функции кодирует значения, включая пробелы и `&`, и
пропускает пустые параметры. Пример: `/api/products?search=North&size=42&max_price=8000&limit=13&offset=0`.
Фильтрацию выполняет БД через существующий бэкенд; фронтенд не фильтрует одну
загруженную страницу. `/api/brands` даёт варианты для списка брендов. Ошибка
брендов не блокирует каталог и остальные фильтры; есть отдельная кнопка повтора.

API возвращает массив без общего количества. Для страницы размера N запрашиваем
N+1 записей: показываем первые N, по дополнительной определяем доступность
«Далее». Смещение `(page - 1) * N`; число всех страниц не выдумываем.
`AbortController` отменяет предыдущий запрос и запросы при уходе со страницы;
отменённый ответ не может заменить актуальные данные. Ошибка следующей страницы
повторяется с тем же смещением. Фильтры пока не сохраняются в URL: перезагрузка
возвращает исходный каталог.

## F3: регистрация, вход и сессия Pinia

Страница → действие Pinia → API → FastAPI. Общая сессия нужна шапке, профилю,
а в следующих этапах — корзине и заказам. `defineStore('auth', ...)` создаёт
хранилище, `ref` хранит состояние, `computed` вычисляет `isAuthenticated`,
функции становятся действиями (actions). Это аналог общего Angular-сервиса
с реактивным состоянием; компоненты получают тот же экземпляр через `useAuthStore()`.

- `/register` отправляет JSON с email и паролем; 201 показывает приглашение войти.
- `/login` получает JWT, затем запрашивает `/auth/me`. Вход считается успешным
  только после получения профиля. Шапка показывает email, профиль — роль из БД.
- `/account` защищён navigation guard (аналог Angular route guard). Для гостя
  выполняется переход на `/login`. Авторизованный пользователь с `/login` или
  `/register` переводится в профиль.
- JWT сохраняется в `sessionStorage` и проверяется через `/auth/me` после
  обновления вкладки. Профиль не восстанавливается из непроверенного кэша.
  sessionStorage доступен JavaScript этой вкладки; защита от XSS важна.
  Браузер обычно удаляет его при закрытии вкладки, но восстановление вкладок
  может вернуть данные сессии. При запрете хранилища вход работает в памяти.
- Пароль не попадает в Pinia или хранилище, очищается из формы после запроса
  и при смене страницы. Проверяется ограничение bcrypt: 8+ символов, до 72 байт
  UTF-8. Сервер повторно валидирует ввод. Ошибки 401/409/422 показаны по-русски.
- `authorizedRequest` добавляет `Authorization: Bearer ...`. Ответ 401 очищает
  текущую сессию и предлагает войти снова. Ответ 403 сохраняет вход: это отказ
  в доступе, а не признак неверного токена. Неавторизованный вход с неверным
  паролем обрабатывается отдельно и показывает ошибку в форме.
- Сетевой сбой при восстановлении не удаляет сохранённый JWT: доступны повтор
  проверки и выход. Таймаут новых HTTP-запросов — 10 секунд. Публичный каталог
  загружается независимо от восстановления сессии.
- Выход очищает локальные данные. Счётчик `revision` не позволяет старому ответу
  восстановить пользователя после выхода или удалить более новую сессию по 401.
  Форма отменяет запрос при уходе со страницы.

JWT на сервере действует 15 минут; refresh endpoint отсутствует. Окончание
сессии обнаруживается при проверке профиля или другом защищённом запросе.
Клиентский выход не отзывает уже выданный JWT на сервере. Guard и отображение
роли управляют интерфейсом; права на данные проверяет FastAPI.

Существующие запросы публичного каталога сохранены отдельно. `api/http.client.ts`
используется для новых auth-запросов и последующих защищённых запросов.

## Соглашения: имена файлов и стили

По результатам ревью роли файлов обозначаются суффиксами:

- `api/auth.api.ts`, `api/catalog.api.ts` — запросы домена и типы API.
- `api/http.client.ts` — общий HTTP-клиент для auth и защищённых запросов.
- `stores/auth/auth.store.ts` — состояние и действия сессии Pinia.
- Компоненты и страницы именуются в PascalCase, например `ProductCard.vue`,
  `CatalogView.vue`. Для таблицы маршрутов оставлен обычный `router/index.ts`.

Все импорты и проверки обновлены. Имена и пути HTTP-эндпоинтов остались прежними:
переименование файла не меняет адрес `/api/auth/login`.

В `src/styles.css` находятся цвета темы (CSS-переменные), базовые правила для
страницы, ссылок и полей, общие кнопки, `.eyebrow`, `.hint-text`, `.error-text`
и утилита `.visually-hidden`. Стили конкретного компонента, включая его
медиазапросы, находятся в `<style scoped>` этого `.vue` файла:

- `App.vue` — композиция и ширина общего контейнера.
- `components/layout/AppHeader/AppHeader.vue` — шапка и навигация по состоянию входа.
- `components/layout/AppFooter/AppFooter.vue` — подвал.
- `components/auth/SessionMessages/SessionMessages.vue` — сообщения сессии и кнопки повтора/выхода.
- `ProductCard.vue` — изображение, цена, размеры и доступность товара.
- `CatalogFilters.vue` — сетка полей и действия формы.
- `CatalogView.vue` — вступление, сетка товаров, состояния и пагинация.
- `AuthView.vue` — форма входа/регистрации и сообщение об успехе.
- `AccountView.vue` — оформление профиля.

`scoped` добавляет CSS-селекторам атрибут компонента, как стандартная инкапсуляция
стилей Angular. Общие цвета и шрифт продолжают наследоваться. `:deep` здесь
не нужен: внутренний вид дочерних компонентов задаётся в них самих.
Небольшой одинаковый контейнер страниц входа и профиля пока описан в каждом
компоненте; отдельный layout-компонент для этого этапа не требуется.

## Композиция App.vue после ревью

Корневой компонент занимает 28 строк: импортирует шапку, сообщения сессии,
RouterView и подвал. Общая ширина задаётся классом `app-container` в его
scoped-стилях; внутреннее оформление находится в дочерних компонентах.

Шапка и сообщения читают одну сессию через `useAuthStore()`, поэтому корню
не требуется передавать токен и пользователя через props. Подвал статический.
Аналог в Angular: app component собирает header, router-outlet и footer.

Реакция на выход из уже открытого профиля вынесена в
`router/session-navigation.ts`. Наблюдатель подключается один раз в `main.ts`
после Pinia; при размонтировании приложения отписывается через `app.onUnmount`.
Он дополняет guard: guard проверяет переход на страницу, наблюдатель реагирует
на изменение сессии, когда страница уже открыта. Pinia не импортирует Router.

После разделения прошли сборка и 16 проверок сессии/навигации. В Chrome
проверены внешний вид профиля, шапки и подвала и переход на `/login` при выходе.
Пользователь завершил ревью и разрешил локальный коммит.

## F4: выбор размера и добавление в корзину

Путь данных: `ProductCartForm` → `cart.store` → `cart.api` → авторизованный
HTTP-клиент → FastAPI. `ProductCard` отвечает за вид товара, а отдельная форма
содержит радио-кнопки размера и количество. Размеры без остатка отключены.
Добавление требует явно выбранного размера и целого положительного количества.
Для гостя доступен переход ко входу с возвратом в каталог.

POST `/cart/items` отправляет только `product_size_id` и `quantity`: ID размера,
а не товара. При повторном добавлении сервер увеличивает существующую позицию.
Клиент учитывает уже добавленное количество, но окончательную проверку остатка
всё равно выполняет сервер. Добавление не резервирует и не списывает товар.

`cart.store.ts` хранит серверный снимок `Cart | null`. `null` означает, что
актуальные данные неизвестны; это отличается от подтверждённой пустой корзины.
После входа/восстановления запускается GET `/cart`. Счётчик в `CartLink` показывает
сумму количеств, а не число строк. `CartView` и `CartLine` показывают размер,
количество, цену и предварительную сумму. Денежные суммы приходят с сервера
строками; `format-price.ts` используется только для их отображения.

Запись сериализована: пока выполняется добавление, другие кнопки добавления
и обновления отключены, а хранилище также проверяет повторный вызов. После
подтверждённого POST выполняется GET всей корзины. Если этот GET не удался,
сообщение всё равно подтверждает добавление и предлагает обновить данные.
Если ответ POST потерян, автоматического повтора нет: сначала нужно загрузить
корзину и проверить её состояние. Это отличается от идемпотентного оформления
заказа, которое мы разбирали на бэкенде.

При выходе или смене токена хранилище синхронно очищается и отменяет запросы.
Счётчик версии не позволяет старому ответу подменить корзину новой сессии.
401 обрабатывает существующий auth.store; 409 `insufficient_stock` показывается
как нехватка товара, 404 — как недоступный размер. После ошибки добавления
сначала требуется обновить корзину. Токены, пароли и корзина не сохраняются
в дополнительное браузерное хранилище: состав корзины хранится в БД.

`/cart` защищён guard. Гостевой переход ведёт на `/login?next=cart`, успешный
вход возвращает в корзину. `next` допускает только известные имена страниц,
произвольные внешние адреса не используются. Просмотр и добавление закрывают
этот этап; редактирование и удаление позиций добавим следующим этапом.

## F5: изменение количества и удаление позиции

`CartItemActions.vue` содержит черновик количества, кнопку «Сохранить» и удаление.
`CartLine.vue` отвечает за информацию о позиции и подключает эти действия.
Изменение поля само по себе не отправляет запрос: форма применяется кнопкой
или Enter. Нулевое количество не означает удаление, для удаления есть кнопка.
При нулевом складском остатке изменение отключено, удаление остаётся доступным.

API-функция PATCH `/cart/items/{item_id}` передаёт `{quantity}` и задаёт конечное
количество: повторное значение 2 оставляет 2 пары. DELETE той же позиции
возвращает пустой 204, который HTTP-клиент корректно принимает. Используется
ID строки корзины, а не товара/размера. Интерфейс `CartQuantity` переиспользуется
для запроса изменения, `CartAdd` и ответа `CartItem`.

`mutateCart` объединяет запись, блокировку параллельных действий, защиту сессии
и обновление по GET для add/update/remove. Во время записи старый подтверждённый
состав остаётся виден с заблокированными действиями. После успешного GET
обновляются позиции, подытоги, общая сумма и счётчик; страница показывает
сообщение «Количество обновлено» или «Позиция удалена». Черновик другой позиции
не сбрасывается, если её серверное количество не изменилось.

При 404 показывается недоступная позиция, при insufficient_stock — нехватка
остатка, при 422 — ошибочный ввод. При неизвестном результате сначала нужна
загрузка корзины. Подтверждённая запись с неудачным GET не выдаётся за неудачную
запись и не повторяется автоматически. Отмена/смена сессии защищены общим
счётчиком версии и AbortController.

## F6: оформление заказа

`api/orders.api.ts` описывает ответ заказа и POST `/orders`. Тело — `{}`:
сервер сам читает позиции корзины, проверяет склад и рассчитывает итог.
Цена покупки приходит строкой Decimal; фронтенд форматирует её для отображения.

Оформление — действие `placeOrder` существующего `stores/cart/cart.store.ts`.
Оно использует общую блокировку записи корзины, обновляет её после заказа
и хранит подтверждённый результат для `components/cart/CheckoutPanel/`.

в `CheckoutPanel.texts.ts`, сообщения действия — в `stores/cart/checkout.texts.ts`.

Перед POST сохраняется случайный `Idempotency-Key` в sessionStorage
под ключом, связанным с ID пользователя. Если хранилище недоступно, POST
не отправляется. При сетевом сбое или 5xx результат считается неизвестным:
кнопка «Уточнить результат оформления» повторяет POST с тем же ключом.

Переход между страницами и перезагрузка вкладки сохраняют незавершённый ключ.
401 завершает сессию; ключ остаётся для повторного входа того же пользователя.
Старые ответы после выхода или смены пользователя игнорируются.

Успешный POST показывает номер, сумму, статус и количество позиций заказа.
После него GET обновляет корзину и счётчик. Ошибка GET не отменяет результат
заказа и не запускает повторную покупку. Однозначный отказ 4xx (например,
недостаточный склад) требует обновления корзины; новая попытка получает новый
ключ. Автоматических повторов оформления нет. Закрытие вкладки завершает
срок жизни sessionStorage; история заказов подключена в F7.

## F7: история и детали заказа

В шапке доступна ссылка «Заказы» на защищённую страницу `/orders`.
Список показывает номер, дату в локальном часовом поясе, статус, серверную
сумму и количество позиций. Загружается 10 записей за страницу: запрос
GET `/orders?limit=11&offset=...` читает одну дополнительную запись,
чтобы определить наличие следующей страницы. Порядок задаёт сервер:
новые заказы идут первыми. Есть обновление, повтор после ошибки и пустое состояние.

Ссылка на карточке открывает `/orders/:orderId`. Такой же переход доступен
после оформления в CheckoutPanel. Страница читает GET `/orders/{id}`,
показывает общую информацию и позиции с кодом размера, количеством
и `price_at_purchase`. Имя товара и числовой размер текущий ответ заказа
не содержит; фронтенд не подменяет исторические данные текущим каталогом.

404 означает, что заказ не найден или недоступен текущему пользователю.
Права доступа проверяет сервер; ID пользователя не отправляется как фильтр.

### Почему без нового Pinia store

Состояние истории и деталей нужно только их страницам. Оно находится
в `composables/orders/useOrderHistory/` и `composables/orders/useOrderDetails/`,
рядом с текстами ошибок. Composable — функция, которая создаёт локальные
reactive refs и методы загрузки; это не общий singleton store.
При уходе со страницы запрос отменяется. При смене сессии данные очищаются
синхронно, запоздавшие ответы игнорируются. При смене orderId тот же экран
загружает другой заказ без повторного создания компонента.

Повторяющаяся сводка вынесена в `components/orders/OrderSummary/`.
Страницы и тексты лежат в `views/OrdersView/` и `views/OrderDetailsView/`.
Маршруты требуют авторизации. После входа можно вернуться к списку или
конкретному заказу: `router/auth-redirect.ts` разрешает только известные
маршруты и положительный целочисленный номер, без внешних URL.

## F9: административное управление товарами

Защищённая страница `/admin/products` доступна по ссылке «Управление товарами»
в шапке администратора. Гость попадает на вход и после него возвращается
в админку; покупатель перенаправляется в профиль с пояснением о правах.
Guard находится в `router/session-guard.ts`. Проверка роли во фронтенде
управляет интерфейсом, окончательная проверка каждой записи остаётся на сервере.
При изменении роли открытая админка закрывается, локальные данные очищаются.

Список загружается по 10 товаров плюс одна запись для проверки следующей
страницы. Для создания и полного PUT-обновления используется общая форма:
название, существующий бренд, цена, описание и необязательный HTTP/HTTPS URL
изображения. Цена хранится строкой, запятая нормализуется в точку; проверяются
положительность и ограничения Numeric(10,2). Размеры не отправляются в теле
товара. Управление размерами и складом — отдельный следующий этап.

Удаление требует явного подтверждения с названием товара. Сервер удаляет
товар и размеры атомарно, запрещая удаление при ссылках из корзины или заказа.
409 объясняется в интерфейсе. Формы и повторные записи блокируются на время
запроса. При 422 черновик остаётся для исправления. При неизвестном результате
записи форма закрывается, действия блокируются до обновления списка и проверки
результата. Подтверждённая запись и неудачный последующий GET отображаются
раздельно, без повторного POST. При 403 действия блокируются до повторного
чтения профиля. При выходе, смене пользователя и уходе со страницы запросы
отменяются, запоздавшие ответы игнорируются.

Структура:

```text
api/admin-products.api.ts
composables/admin/useAdminProducts/
  useAdminProducts.ts
  useAdminProducts.texts.ts
components/admin/
  AdminProductForm/
    AdminProductForm.vue
    AdminProductForm.texts.ts
    AdminProductForm.model.ts
  AdminProductRow/
  AdminProductDelete/
views/AdminProductsView/
```

Состояние страницы локальное, нового Pinia store нет. Форма хранит независимый
черновик и выдаёт ProductWrite через emit, не изменяя Product из списка.
ProductWrite переиспользует поля Product через Pick. `catalogQueryParams`
используется и публичным каталогом, и админкой для одинаковой сериализации
фильтров и пагинации. Компоненты и их тексты находятся рядом.

## F10: размеры и склад товара

В списке управления товарами появилась ссылка «Размеры и склад», ведущая
на `/admin/products/:productId/inventory`. Страница защищена общим guard
администратора и сохраняет адрес для возврата после входа.
Проверка номера товара и заказа использует общий `utils/positive-id.ts`.

Страница загружает Product с размерами через GET `/products/{id}`.
Размеры отображаются по возрастанию значения. Можно добавить вариант,
изменить его размер/остаток и удалить с подтверждением через ConfirmDialog.
Успех использует общий notification store с таймером 3 секунды.

Остаток задаётся как конечное целое количество, а не прибавление; 0 допустим.
Размер положительный, до 999, с одним знаком после запятой. Ввод запятой
нормализуется в точку, API получает строку Decimal. SizeWrite переиспользует
поля ProductSize через Pick, PATCH — Partial от SizeWrite.
Отправляются только изменённые поля: изменение только размера не перезаписывает
остаток, который мог измениться при покупке после открытия формы.
Пустой PATCH не отправляется. Само сохранение абсолютного остатка не имеет
проверки версии: перед установкой конечного количества администратор должен
учитывать актуальные складские данные.

Бизнес-ошибки сервера показываются отдельно: повтор размера, использование
в корзине/заказе, исчезнувший товар/размер, необходимость повторить после
конкурентного изменения. Для связанного размера запрещены переименование
и удаление, но разрешено изменение остатка. После 409 с повтором или ссылками
редактор остаётся доступен для исправления. При неизвестном результате записи
нужен GET перед следующей записью. Подтверждённая запись не повторяется
из-за ошибки последующего чтения. Смена товара в URL, сессии, роли и уход
со страницы отменяют запросы; запоздавшие ответы игнорируются.

Структура:

```text

components/admin/AdminSizeForm/
components/admin/AdminSizeRow/
components/admin/AdminSizeDelete/
views/AdminInventoryView/
```

Форма, строка и подтверждение находятся в отдельных компонентах вместе
со своими текстами. Валидация черновика — рядом в AdminSizeForm.model.ts.
Состояние страницы локальное; новый общий Pinia store не потребовался.
