# Практическое задание: бэкенд интернет-магазина кроссовок

## Цель задания

Ты строишь бэкенд интернет-магазина кроссовок: локальное приложение на Python с базой PostgreSQL и REST API. Оно закрывает полный цикл покупки от каталога до оформления заказа.

Уровень честно: это проект уровня intermediate, не первый скрипт. Поэтому не пиши всё сразу. Задание разбито на 7 модулей (M0–M6). Каждый модуль самодостаточен и проверяется отдельно; после каждого у тебя работает очередной кусок магазина. Двигайся строго по порядку, не перепрыгивай.

Что должно работать в финале: зарегистрироваться, посмотреть каталог с фильтрами, добавить кроссовки в корзину, оформить заказ с проверкой остатков, посмотреть историю своих заказов.

## Стек и окружение

Используй ровно этот набор, ничего лишнего не тащи:


- FastAPI — роуты и автодокументация (Swagger на /docs)
- PostgreSQL — база, поднимаешь в Docker через docker-compose
- SQLAlchemy 2.0 в синхронном режиме — ORM
- Alembic — миграции схемы
- Pydantic — схемы запросов и ответов, валидация
- passlib[bcrypt] — хэширование паролей
- python-jose — генерация и проверка JWT

Требования к окружению:

- Python 3.11+
- отдельный venv
- все зависимости зафиксированы в requirements.txt
- секреты (строка подключения к БД, секрет для JWT) лежат в .env, а не в коде

## Модель данных

Семь таблиц. Спроектируй их на бумаге до того, как писать код.

| Таблица | Поля | Зачем |
| --- | --- | --- |
| users | id, email, hashed_password, is_admin, created_at | пользователи и признак админа |
| brands | id, name | бренды кроссовок |
| products | id, name, brand_id, description, price, image_url, created_at | карточка товара |
| product_sizes | id, product_id, size, stock | размер и остаток на складе |
| cart_items | id, user_id, product_size_id, quantity | позиции в корзине |
| orders | id, user_id, status, total, created_at | заказ |
| order_items | id, order_id, product_size_id, quantity, price_at_purchase | позиции заказа |

Что важно понять на этой схеме:

- Связи один-ко-многим: brand → products, product → product_sizes, order → order_items.
- Остаток (stock) живёт на размере, а не на товаре: у 42-го и 43-го размера своя доступность.
- В order_items цена сохраняется отдельно (price_at_purchase). Это снимок цены на момент покупки: если завтра цена товара изменится, старый заказ должен остаться прежним.
- Корзина привязана к пользователю через user_id, чужую видеть нельзя.

## Модули реализации

Каждый модуль описан в трёх пунктах: Что делаешь, Что понять, Какой результат. Проверяй результат перед переходом к следующему модулю.

### M0 — Окружение

- Что: настрой структуру проекта, venv, зависимости. Подними PostgreSQL в docker-compose. Подключись к базе из FastAPI.
- Понять: зачем базу держат в контейнере, а не ставят в систему; что такое строка подключения DATABASE_URL; как приложение находит базу.
- Результат: /docs открывается, работает тестовый GET /health со статусом ok.

### M1 — БД и модели

- Что: опиши SQLAlchemy-модели всех таблиц. Сделай первую Alembic-миграцию. Напиши seed-скрипт, который заливает пару брендов и несколько кроссовок с размерами.
- Понять: чем модель (таблица в БД) отличается от обычного класса; как relationship связывает таблицы; зачем миграции, а не создание таблиц руками.
- Результат: таблицы создаются миграцией, в базе лежат тестовые данные.

### M2 — Каталог

- Что: CRUD товаров. Список с фильтрами (бренд, размер, диапазон цены), поиском по названию и пагинацией. Создание, редактирование и удаление доступны только админу.
- Понять: разница между GET (чтение) и POST/PUT/DELETE (изменение); что такое query-параметры; зачем нужна пагинация.
- Результат: через API можно листать, искать и фильтровать кроссовки.

### M3 — Пользователи и аутентификация

- Что: регистрация и логин. Хэшируй пароль перед сохранением. Выдавай JWT при логине. Сделай зависимость get_current_user и эндпоинт GET /me.
- Понять: почему пароль нельзя хранить как есть; что лежит внутри JWT и почему это не пароль; чем аутентификация (кто ты) отличается от авторизации (что тебе можно).
- Результат: защищённые роуты требуют валидный токен, без него отдают 401.

### M4 — Корзина

- Что: добавить позицию в корзину, изменить количество, удалить позицию, посмотреть корзину. Корзина принадлежит текущему пользователю.
- Понять: как привязать действие к конкретному юзеру через токен; почему нельзя трогать чужую корзину.
- Результат: корзина работает под конкретным залогиненным пользователем.

### M5 — Заказы

- Что: оформление заказа. Собери заказ из корзины, посчитай сумму, спиши остаток со склада, очисти корзину, присвой статус. Добавь историю заказов и просмотр одного заказа. Смена статуса доступна админу.
- Понять: что такое транзакция и почему списание остатка и создание заказа должны пройти вместе или не пройти вовсе; почему нельзя заказать больше, чем есть на складе.
- Результат: полный цикл покупки закрыт, остатки корректно уменьшаются.

### M6 — Оформление кода

- Что: разложи код по слоям (models, schemas, routers, services). Добавь обработку ошибок с понятными HTTP-кодами. Вынеси настройки в конфиг. Напиши README с инструкцией запуска.
- Понять: за что отвечает каждый слой и почему бизнес-логика не должна жить в роутере.
- Результат: проект читаемый, структурированный, запускается по README с нуля.

## Карта API

Итоговый набор эндпоинтов по доменам. Примерно 18 штук: достаточно, чтобы было большое API, но не бесконечное.

**Каталог**

- GET /products — список с фильтрами, поиском и пагинацией
- GET /products/{id} — один товар
- POST /products — создать (admin)
- PUT /products/{id} — обновить (admin)
- DELETE /products/{id} — удалить (admin)
- GET /brands — список брендов

**Аутентификация**

- POST /auth/register — регистрация
- POST /auth/login — логин, возвращает JWT
- GET /auth/me — текущий пользователь

**Корзина**

- GET /cart — содержимое корзины
- POST /cart/items — добавить позицию
- PATCH /cart/items/{id} — изменить количество
- DELETE /cart/items/{id} — удалить позицию

**Заказы**

- POST /orders — оформить заказ из корзины
- GET /orders — история заказов
- GET /orders/{id} — один заказ
- PATCH /orders/{id}/status — сменить статус (admin)

## Структура проекта

```
sneaker_shop/
  app/
    main.py           # точка входа, подключение роутеров
    database.py       # engine и сессия SQLAlchemy
    core/
      config.py       # настройки, чтение .env
      security.py     # хэш паролей, JWT
    models/           # SQLAlchemy-модели (таблицы)
    schemas/          # Pydantic-схемы (вход и выход API)
    routers/          # эндпоинты по доменам
    services/         # бизнес-логика (оформление заказа)
  alembic/            # миграции
  docker-compose.yml  # PostgreSQL
  requirements.txt
  .env.example
  README.md
```

За что отвечает каждый слой:

- models: как данные лежат в базе.
- schemas: как данные приходят и уходят через API, плюс валидация ввода.
- routers: принимают запрос, вызывают сервис, возвращают ответ. Логики тут минимум.
- services: вся бизнес-логика (посчитать сумму, проверить и списать остаток).

Правило: models, schemas, routers и services — это разные вещи. Если начинаешь считать сумму заказа прямо в роутере, стоп: это работа сервиса.

## Блок проверок и тестов

Прогони эти проверки руками через Swagger (/docs) перед сдачей модуля и в самом конце:

- /docs открывается, все эндпоинты видны и вызываются.
- Нельзя заказать больше, чем есть на складе: сервер возвращает ошибку, а не уходит в минус.
- Корзина и заказы недоступны без токена: отдают 401.
- Обычный пользователь не может создать или удалить товар: отдаёт 403.
- Сумма заказа считается корректно (проверь на нескольких позициях с разной ценой).
- После оформления заказа остаток на складе уменьшился, а корзина очистилась.
- Миграции проходят с нуля на чистой базе.
- Pydantic отклоняет мусор: отрицательная цена, пустой email, количество ноль или меньше.

Это главная часть задания. Отдельным файлом CONCEPT.md напиши своими словами, без копипасты из документации, ответы на:

2. Зачем нужна база данных и что описывает твоя схема: какие таблицы и как они связаны.

Критерий: если можешь объяснить это простыми словами так, чтобы понял человек без опыта, значит ты действительно разобрался, а не просто собрал код. Место, где получается работает, но не знаю почему, это и есть место для доработки.
