# Бэкенд магазина кроссовок: полный учебный проект M0–M6

FastAPI + PostgreSQL + синхронный SQLAlchemy2. Каталог, регистрация и JWT, личная корзина, атомарный заказ, своя история и административные операции. Это запускаемый эталон для [презентации](../sneaker-backend.html). Финальная точка входа — **`app.final_main:app`**. Старый `app.main:app` оставлен как пример M0–M1 с `/health`.

Нужны Python3.11+, Docker с Compose v2 и доступ к пакетам для первоначальной установки. Проверено на **macOS, Python3.13.3, PostgreSQL17**. Команды для PowerShell приведены, но запуск на Windows не проверялся. PostgreSQL запускается в Docker, Python-приложение — в venv на хосте. Учебный сервер привязан к localhost.

## 1. Открыть корень проекта и создать venv

Из корня репозитория:

```sh
cd presentation/sneaker-practice
```

Если получили отдельно папку проекта, откройте её: рядом должны лежать `requirements.txt`, `compose.yaml`, `alembic.ini` и `app/`. **Все дальнейшие команды выполняются из этой папки.**

macOS/Linux:

```sh
python3 --version
python3 -m venv .venv
source .venv/bin/activate
```

Windows PowerShell:

```powershell
py -3 --version
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
```

Если активация недоступна, используйте `.venv/bin/python` либо `.\.venv\Scripts\python.exe` вместо `python`. Выберите установленный Python3.11+; проверенный интерпретатор этого комплекта —3.13.3.

```sh
python -c "import sys; print(sys.executable)"
python -m pip install -r requirements.txt
python -m pip check
```

Путь Python должен вести в новый `.venv`, проверка пакетов — сообщить `No broken requirements found.`. Финальный [requirements.txt](requirements.txt) содержит полный закреплённый стек. Для старой главы M0–M1 базовый список сохранён в [requirements-m01.txt](requirements-m01.txt); [requirements-m3.txt](requirements-m3.txt) сохранён для повторения команд M3–M5. Не устанавливайте базовый список вместо полного при финальном запуске.

## 2. Создать локальные настройки

Только если `.env` ещё нет, скопируйте [.env.example](.env.example).

macOS/Linux, с сохранением существующего файла:

```sh
if [ ! -f .env ]; then cp .env.example .env; fi
```

PowerShell:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Затем:

```sh
python setup_jwt.py
```

Команда запишет случайный локальный JWT_SECRET, не печатая значение. Непустой существующий ключ не заменяется; config требует не менее 32 символов. `.env` хранит конфигурацию только для вашей локальной копии и исключён из Git.

| Переменная | Назначение |
|---|---|
| POSTGRES_USER / POSTGRES_PASSWORD | Учётная запись учебной БД в Compose |
| POSTGRES_DB | Имя рабочей учебной базы |
| DB_PORT | Опубликованный порт хоста, по умолчанию 55433 |
| DATABASE_URL | Подключение Python к `127.0.0.1:55433`, драйвер `postgresql+psycopg` |
| JWT_SECRET | Локальный ключ подписи токенов |

В примере — вымышленные учебные значения. При изменении портов или реквизитов согласуйте DATABASE_URL с Compose. Внутри контейнера БД слушает 5432. [config.py](app/core/config.py) читает `.env` из корня проекта, но уже заданные переменные процесса имеют приоритет; прежняя настройка терминала может перекрыть новый файл.

## 5. Пройти покупку в Swagger

1. `POST /auth/register`: вымышленный email Ани и учебный пароль от 8 символов, не более 72 байт UTF-8. Ожидается 201. `is_admin` не передаётся.
2. `POST /auth/login` с теми же данными:200 и access_token. В Authorize вставьте **только значение токена**, без кавычек и Bearer. `GET /auth/me` должен показать Аню. Используем `/auth/me` из карты API задания, а не краткую запись `/me` в описании M3.
3. `GET /products/10`: найдите размер 101; у товара 20 — размер 201. `product_id` и `product_size_id` не взаимозаменяемы.
4. `POST /cart/items`: `{"product_size_id":101,"quantity":2}`, затем `{"product_size_id":201,"quantity":1}`. Оба ответа 200. `GET /cart` на исходном seed: две строки, три пары, estimated_total `"21970.00"`.
5. `POST /orders` с `{}` либо без тела:201, status `created`, total `"21970.00"`. **Сохраните id из своего ответа.**
6. `GET /orders` и `GET /orders/{id}`: виден свой заказ со снимками цен. Корзина пуста, stock101=1, stock201=4.
7. Войдите Борисом: чужая карточка заказа 404. Без токена корзина и заказы 401.

Повторный POST корзины **прибавляет** quantity, PATCH по id строки корзины задаёт абсолютное число. DELETE204 без тела. Корзина не резервирует склад, а её сумма ориентировочная. При повторной демонстрации проверьте текущие данные: stock после покупки уже изменился. Не удаляйте том для получения красивых исходных цифр; изолированная проверка ниже создаст собственную новую базу.

## 6. Проверить администратора

Сначала зарегистрируйте отдельный вымышленный `admin@example.com` через API. Затем в другом терминале, из того же корня и venv:

```sh
python -m app.promote_admin admin@example.com
```

Команда изменяет существующий аккаунт, а не создаёт пароль по умолчанию. Выполните login администратором, Authorize и `/auth/me`: `is_admin=true`. Административные POST/PUT/DELETE каталога доступны этому пользователю. Обычному пользователю —403.

`PATCH /orders/{id}/status` принимает `{"status":"processing"}`, затем `completed`. Разрешены `created → processing → completed`; повтор текущего статуса 200 без эффекта, обратный ход или пропуск 409, неизвестное значение 422. Stock повторно не списывается. GET истории и карточки остаются личными даже для администратора.

## Идемпотентность оформления заказа

В `POST /orders` доступен необязательный заголовок `Idempotency-Key`.
Одна самостоятельная покупка — один ключ; все сетевые повторы этой покупки
используют тот же ключ. Пример запроса:

```http
POST /orders
Authorization: Bearer <ваш токен>
Idempotency-Key: checkout-demo-1

{}
```

В Swagger заголовок задаётся в поле **Idempotency-Key** у POST /orders.
Допустимы 1–128 ASCII-символов: буквы, цифры, `.`, `_`, `:`, `-`.
Пустой, некорректный или повторённый заголовок отклоняется с 422.
Тело по-прежнему `{}` или отсутствует; лишние поля отклоняются даже при повторе.

Первая успешная покупка сохраняет заказ и снимок JSON-ответа в одной
транзакции. Повтор с тем же пользователем и ключом возвращает **201 и тот же
JSON** до чтения корзины: склад повторно не списывается, новая корзина
не оформляется и не очищается. Ключи разных пользователей независимы;
авторизация требуется при каждой попытке, ключ не заменяет токен.

В снимке остаётся исходный status `created`, даже если заказ затем обработан.
Актуальный статус читается через GET /orders/{id}.
Без заголовка сохраняется прежнее поведение: новая покупка из текущей
корзины, повтор после очистки — 409 `empty_cart`.

Неуспешная покупка ключ не занимает: после отката или устранения нехватки
остатка его можно повторить. Одновременные запросы одного пользователя
согласуются блокировкой User; успешные повторы одного ключа вернут один
заказ. При превышении таймаута ожидания возможен 409 `concurrent_change_retry`;
следующую попытку отправляйте с тем же ключом. Проверка replay всё равно
может ждать пользовательскую блокировку: это не отдельный кэш без БД.

Записи ключей сейчас не удаляются автоматически. Повтор защищён, пока запись
хранится; удаление записи или downgrade `0002` снимает эту гарантию.
Старые заказы, оформленные без ключей, задним числом к ключам не привязываются.
Для новой покупки обязательно создайте новый ключ. При одинаковом пустом
теле сервер не может определить, что клиент хотел другую покупку со старым ключом.
В Angular генерируйте UUID один раз вне повторяемой части запроса и сохраняйте
для повторов; создание нового ключа в каждой попытке обходит защиту.

## Управление размерами и остатками — расширение финального приложения

Новые операции доступны только администратору в `app.final_main:app`.
Учебные точки M0–M5 сохраняют прежний набор маршрутов.
Таблица `product_sizes` уже существует, новая миграция не требуется.

| Метод и путь | Тело | Результат |
|---|---|---|
| `POST /products/{product_id}/sizes` | `{"size":"42.0","stock":3}` | 201, размер с новым id |
| `PATCH /products/{product_id}/sizes/{size_id}` | `{"stock":5}` или `{"size":"42.5"}` | 200, обновлённый размер |
| `DELETE /products/{product_id}/sizes/{size_id}` | Нет | 204 без тела |

PATCH задаёт **абсолютный** stock, не прибавляет его. Можно передать оба поля.
Пустое тело, null, лишние поля, отрицательный stock, дробный/строковый/bool stock
и значения за пределами PostgreSQL integer отклоняются с 422.
Размер положительный, не больше 999, с максимум одним дробным знаком.

Размер уникален в пределах товара; дубликат при создании или изменении —
409 `size_already_exists`. Неизвестный товар при создании — 404
`product_not_found`; неизвестный размер или размер другого товара при
PATCH/DELETE — 404 `size_not_found`.

Размер, используемый корзиной или заказом, нельзя удалить или переименовать:
409 `size_referenced`. Его stock менять можно, включая установку 0.
Это может сделать существующую корзину неоформляемой: checkout проверяет
остатки заново и возвращает 409 без частичной покупки.
Повтор передачи того же размера вместе с новым stock не считается переименованием.

Пример покупки нового товара: создайте карточку через POST /products,
создайте её размер, затем под обычным пользователем добавьте **id размера**
в корзину и оформите заказ. Размеры читаются в публичной карточке товара.

Все записи выполняются в свежей транзакции; роль администратора повторно
проверяется и удерживается на время записи. PATCH/DELETE блокируют строку
размера через FOR UPDATE, согласуя изменения с корзиной и checkout.
Конфликт уникальности откатывает весь PATCH, включая изменение stock.

## Логи запросов и ошибок

Финальное приложение пишет JSON-логи в терминал сервера, по одной записи
на HTTP-запрос. Используется стандартный logging, новые зависимости и
миграции не нужны. Реализация: `app/core/request_logging.py`.

В ответах, включая 401/404/422 и безопасный 500, есть **X-Request-ID**.
Это новый UUID для каждой HTTP-попытки; входной X-Request-ID не принимается
на доверии и заменяется серверным. Он также доступен в `request.state.request_id`.
В Swagger идентификатор находится в **Server response → Response headers**.

Пример основных полей записи:

```json
{"event":"http_request","request_id":"13893e80-9049-40bd-8cdb-567251f58dd8","method":"GET","path":"/health","status":200,"duration_ms":29.884}
```

Полная запись содержит UTC timestamp, level и признаки начала/завершения
ответа. `duration_ms` включает ожидания во время обработки на сервере,
это не только время SQL и не время отрисовки Angular.
Для обычных и ожидаемых 4xx используется INFO, для 5xx/исключений — ERROR.

В path пишется **шаблон маршрута**, например `/products/{product_id}`,
а не значения параметров. Неизвестный путь обозначается `/<unmatched>`.
Query-параметры, тела, cookies, Authorization, пароли и токены не логируются.
Стандартный access-log Uvicorn отключён для финального процесса, поскольку
он выводит полный URL. Служебные сообщения запуска Uvicorn остаются.

Непредвиденная ошибка до отправки ответа возвращает 500:

```json
{"detail":"internal_server_error","request_id":"<UUID запроса>"}
```

В ERROR-записи есть тип исключения и безопасные координаты кода
(имя файла, строка, функция). Текст исключения, SQL-параметры, исходные
строки traceback и локальные переменные исключены: они могут содержать секреты.
Обработчики бизнес-ошибок и валидации сохраняют прежний JSON-контракт.
Если ответ уже начат, заменить его код на 500 нельзя: лог помечает ошибку
и фактические признаки отправки; наружу передаётся безопасное исключение
без первоначального текста.

В Angular можно прочитать X-Request-ID из полного HTTP-ответа/ошибки
и показать его рядом с сообщением. При прямом cross-origin доступе CORS
должен разрешать чтение этого заголовка; при dev proxy запрос остаётся
на origin фронтенда. Сам CORS этим изменением не настраивается.

X-Request-ID обозначает **одну HTTP-попытку**. Idempotency-Key связывает
**повторы одной покупки**: при повторе ключ покупки тот же, request_id новый.

## 7. Воспроизвести проверки

БД должна быть запущена. Проверки используют учебную учётную запись с правом создавать/удалять свои временные базы.

```sh
python verify_final.py
```

Скрипт создаёт временную копию без старых `.env`/`.venv`, устанавливает зависимости в новый venv, создаёт пустую БД на текущем PostgreSQL. Проверяет миграцию 0001→0002 и обратный переход на тестовых данных, затем seed, безопасные HTTP-логи, финальный Uvicorn и все 21 операцию. Второй seed проверяется на неизменность данных. В этом же новом окружении проходят проверки схемы/seed, M2–M3 и M4–M5 на их отдельных временных базах.

Получен [отчёт](final-verification.json): **134 финальные проверки (43 базовые,57 склада,34 идемпотентности),23 диагностики,25 схемы/seed,85 M2–M3,76 M4–M5 — всего 343**. Отдельно проверено сохранение семи прежних таблиц при upgrade/downgrade. Диагностика проверяет независимость UUID параллельных запросов, безопасный 500 и реальный вывод Uvicorn без секретных маркеров. Проверки идемпотентности включают потерянный ответ, новый процесс сервера, новую корзину, изменённые цены/статус, изоляцию пользователей, откат после записи ключа и наблюдаемые HTTP-гонки. Свежая установка Docker/новая ОС этим не проверяются: сервер PostgreSQL уже запущен. `/docs` проверяется как HTTP HTML, схема — через OpenAPI; ручной UI-сценарий нужен отдельно. В конце удаляются только созданные временные базы и папка, рабочий том сохраняется.

Отдельные уже подготовленные проверки:

```sh
python verify_m23.py
python verify_m45.py
```

Они проверяют фильтры, права, вход, корзину, снимки цен, три прямых ORM-отката и три реальные HTTP-гонки с наблюдаемым ожиданием в PostgreSQL. Детали — в [M4–M5](M4-M5.md). Отчёты не сохраняют пароли, JWT или строку подключения.

## Структура и границы проекта

| Файлы | Роль |
|---|---|
| `app/models/` | Семь таблиц магазина и checkout_requests, связи и ограничения |
| `app/schemas/` | Вход, валидация и ответ API |
| `app/routers/` | HTTP-маршруты и зависимости |
| `app/services/` | Каталог, auth, корзина, checkout и статусы |
| `app/services/unit_of_work.py` | Свежая Session, общая транзакция и контролируемые конфликты |
| `app/core/`, `dependencies.py`, `database.py` | Настройки, безопасность, пользователь и соединения |
| `alembic/` | Версионируемая схема |

Авторизация читает User в своей Session; сервис checkout получает user.id и открывает новую. Общий User lock согласует корзину и покупку, размеры блокируются по id, цены удерживаются FOR SHARE. Все записи входят в одну транзакцию. Цена покупки фиксируется в OrderItem. Подробности — [M6 и финал](M6-FINAL.md).

Это локальный учебный проект без оплаты и доставки. Идемпотентность реализована для POST /orders с ключом и не распространяется автоматически на другие операции. Если ответ потерян при покупке без ключа, сначала сверяйте историю. Допустимые статусы и коды ошибок — выбранный учебный контракт, описанный в модулях.

## Если запуск не получился

| Симптом | Что проверить |
|---|---|
| ModuleNotFoundError | Текущий Python из venv; установлен полный requirements.txt |
| Нет DATABASE_URL / короткий JWT_SECRET | `.env` в корне, setup_jwt.py, переменные терминала |
| /health503 | Docker работает, сервис здоров, порт и URL согласованы |
| Таблица не найдена | `alembic upgrade head` выполнен для той же БД |
| В Swagger только health | Запущен старый app.main; нужен app.final_main |
| После login всё ещё 401 | В Authorize вставлен access_token, проверьте /auth/me |
| Администратор получает 409 на удаление | Товар может иметь связанные размеры/историю; роль не отменяет правила данных |
