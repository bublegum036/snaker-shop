# Мой разбор магазина

## 1. API, REST и группы эндпоинтов

API — это способ общения между фронтендом и бэкендом. Клиент отправляет
запросы для получения данных или выполнения действий, сервер возвращает
статус, заголовки и обычно тело ответа.

REST — стиль организации API вокруг ресурсов. В нашем магазине это товары,
корзина и заказы. GET используется для чтения, POST — для создания,
PUT/PATCH — для изменения, DELETE — для удаления.

Каталог позволяет посмотреть и найти товары. Корзина собирает выбранные
позиции перед покупкой. При оформлении сервер создаёт заказ, сохраняет
цены и сумму, уменьшает остатки и очищает корзину. Заказы можно посмотреть
в истории.

Аутентификация подтверждает личность пользователя, авторизация проверяет
его права. Каталог доступен без входа, корзина и заказы требуют токен,
управление каталогом — права администратора.

Например, GET `/products` возвращает страницу товаров, POST `/auth/login`
проверяет данные входа и выдаёт JWT, GET `/orders` возвращает личную
историю заказов.

## 2. База данных и связи

База данных хранит пользователей, каталог, корзины, заказы и остатки.
Данные сохраняются между перезапусками приложения и используются
централизованно. Бэкенд выполняет правила оформления и пополнения,
а БД сохраняет изменения и обеспечивает их целостность.

| Таблица | Что хранит |
|---|---|
| `users` | Пользователей |
| `brands` | Бренды |
| `products` | Карточки товаров и текущие цены |
| `product_sizes` | Размеры и остатки |
| `cart_items` | Позиции корзин и количества |
| `orders` | Владельца, статус, сумму и дату заказа |
| `order_items` | Позиции заказа и цены покупки |
| `checkout_requests` | Ключи идемпотентности и сохранённые ответы |

Первые семь таблиц относятся к заданию, восьмая добавлена для идемпотентности.

Один бренд может иметь несколько товаров, один товар — несколько размеров.
Остаток хранится у конкретного размера, чтобы учитывать их доступность отдельно.

Один заказ содержит несколько позиций. Общие данные находятся в `orders`,
позиции — в `order_items`, связанных через `order_id`. Так общие данные
заказа не дублируются.

Корзина и заказы связаны с пользователем через `CartItem.user_id`
и `Order.user_id`. У пользователя может быть несколько заказов.

`price_at_purchase` сохраняет цену покупки. Изменение цены в каталоге
не меняет сумму старого заказа.

## 3. Путь оформления заказа

Пользователь оформляет покупку через POST `/orders`. Клиент передаёт JWT
для определения пользователя и пустое тело `{}`. Для безопасных повторов
передаётся `Idempotency-Key`.

Сервис открывает транзакцию. Если результат с таким ключом уже сохранён
для пользователя, возвращается первоначальный ответ без новой покупки.

При первой попытке сервер получает позиции корзины, блокирует строки
размеров и читает текущие цены товаров. Проверяет остатки и рассчитывает
сумму. Сумма вычисляется на сервере, поскольку цена могла измениться,
а клиентские данные можно подменить.

Если хотя бы одной позиции не хватает, возвращается `409 insufficient_stock`.
Заказ не создаётся, остатки и корзина сохраняются.

Если проверки прошли, создаются заказ и позиции с ценами покупки,
списываются остатки и очищается корзина. При наличии ключа сохраняется
ответ. Всё выполняется в одной транзакции: `commit` сохраняет изменения
вместе, ошибка до него откатывает их. После успеха возвращается `201`
и JSON заказа.

Блокировки согласуют одновременные покупки: второй покупатель ждёт
и после покупки последней пары первым получает отказ из-за нулевого остатка.

Если ответ потерялся, запрос повторяется с тем же ключом. Сервер возвращает
прежний заказ без повторного списания. Мы проверили это на заказе №3:
обе попытки вернули один заказ, остаток уменьшился с 5 до 4 только один раз.

## 4. Слои приложения на примере POST /orders

Код разделён на `models`, `schemas`, `routers` и `services`. Models
описывает таблицы и связи БД. Schemas определяет допустимые запросы
и ответы и проверяет данные. Routers принимает HTTP-запрос и вызывает
сервис. Services выполняет бизнес-логику.

| Часть | Реализация |
|---|---|
| Модели | `app/models/entities.py`: `Order`, `OrderItem` и другие |
| Схемы | `app/schemas/orders.py`: `CheckoutRequest`, `OrderRead` |
| Роутер | `app/routers/orders.py`: `checkout` |
| Сервис | `app/services/orders.py`: `checkout` |
| Определение пользователя | `app/dependencies.py`: `get_current_user` |
| Session | `app/database.py`: `SessionLocal` |
| Транзакция | `app/services/unit_of_work.py`: `transaction` |

Зависимость проверяет JWT и получает пользователя. Схема проверяет тело
запроса, роутер передаёт данные сервису. Сервис читает данные через Session,
проверяет остатки, считает сумму и выполняет оформление.

Все изменения входят в одну транзакцию. Отдельные функции не должны
делать собственные commit: иначе ошибка следующего шага оставит частично
выполненную покупку. При успехе сохраняются все изменения, при ошибке —
откатываются. Сервис формирует `OrderRead`, который возвращается клиенту
как JSON.
