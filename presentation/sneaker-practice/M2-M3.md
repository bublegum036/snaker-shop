# Практика M2–M3: каталог, регистрация и права

Главы 13–14 [презентации](../sneaker-backend.html), слайды 137–156. Начало — работающие M0–M1 и исходный каталог 2 бренда / 3 товара / 4 размера. Результат — чтение, фильтры, поиск, пагинация и защищённое изменение карточек, регистрация, JSON-логин, JWT и `/auth/me`.

В комплекте сохранены точки запуска разных этапов. Они используют одну БД и общие модели/сервисы; это учебные состояния одного проекта:

| Точка запуска | Что подключено |
|---|---|
| `app.main:app` | M0–M1: `/health` |
| `app.catalog_main:app` | M2: `/health` и публичные GET каталога |
| `app.store_main:app` | M3: каталог, auth и защищённая запись |

В своём проекте можно последовательно развивать один `main.py`. Отдельные точки в эталоне позволяют проверить, что запись не открывалась до появления авторизации. Корзина и заказы API реализованы в продолжении [M4–M5](M4-M5.md) с отдельными точками запуска. Исторические строки в проверке удаления создаются только как временная тестовая фикстура.

## Подготовка

Откройте терминал в `presentation/sneaker-practice` либо в корне своей сборки. Подготовка Python, `.env` и Docker описана в [M0–M1](README.md).

Для macOS/Linux:

```sh
source .venv/bin/activate
```

Для PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

Поднимите учебный сервис и примените существующую миграцию:

```sh
docker compose up -d --wait
python -m alembic upgrade head
python -m app.seed
```

Seed не сбрасывает изменённые цены и остатки. Примеры ниже рассчитаны на исходные строки. Если вы уже редактировали рабочую БД, сверяйте её состояние; для точного воспроизведения исходного состояния используйте `verify_m23.py`, который создаёт новую временную БД. Рабочий том удалять не нужно.

## M2, шаг 1. Публичный каталог

Промпт `m2_read` на слайде138 и в [m23-prompts.json](m23-prompts.json). В собственной работе подключите только GET. В эталоне:

```sh
python -m uvicorn app.catalog_main:app --reload --port 8000
```

Откройте [Swagger](http://127.0.0.1:8000/docs). Попробуйте:

| Запрос | Результат на seed |
|---|---|
| `GET /brands` | 200, North и City |
| `GET /products` | 200, ID10,20,30 |
| `GET /products/10` | 200, North Runner, цена `"7990.00"`, два размера |
| `GET /products/999` | 404 |

Полный ответ карточки:

```json
{
  "id": 10,
  "name": "North Runner",
  "brand_id": 1,
  "price": "7990.00",
  "description": "",
  "image_url": null,
  "sizes": [
    {"id": 101, "size": "42.0", "stock": 3},
    {"id": 102, "size": "43.0", "stock": 0}
  ]
}
```

Порядок размеров не является контрактом; сортировка списка **товаров** — по ID. Денежные значения и размер в JSON представлены строками Decimal.

Путь запроса: [роутер](app/routers/catalog.py) → [сервис](app/services/catalog.py) → SQLAlchemy/PostgreSQL → [ProductRead](app/schemas/catalog.py). `selectinload` загружает размеры для выбранных товаров; `from_attributes` позволяет Pydantic читать ORM-атрибуты.

В точке M2 `POST /products`, `PUT /products/{id}`, `DELETE /products/{id}` не зарегистрированы. На существующих путях попытки этих методов дают405, состояние БД сохраняется. Это отсутствие метода на данном этапе, а не готовая проверка роли.

## M2, шаг 2. Схемы и контракт карточки

Промпт `m2_schema`, слайд139. Входная `ProductWrite` и ответ `ProductRead` отделены от ORM.

| Поле входа | Правило |
|---|---|
| name | 1–120 символов после очистки крайних пробелов; только пробелы запрещены |
| brand_id | Положительный int в диапазоне ID PostgreSQL |
| price | Decimal > 0, Numeric(10,2), до двух дробных знаков; NaN/Infinity запрещены |
| description | До2000 символов, по умолчанию пустая строка |
| image_url | HTTP/HTTPS URL либо null, по умолчанию null |
| Любое лишнее поле | 422 через `extra='forbid'` |

`id`, `created_at`, роль и размеры не принимаются во входе карточки. `HttpUrl` перед Text-колонкой переводится в строку. Существование бренда проверяется отдельно в БД: `brand_id=999` может пройти проверку формы, но при записи получить409.

Для PUT используется ProductUpdate: дополнительно обязательна положительная `version` из GET карточки; устаревшая версия даёт 409 `product_version_conflict`, успешная запись увеличивает её. PUT заменяет редактируемые поля карточки: `name`, `brand_id`, `price` обязательны. Пропущенные `description` и `image_url` заменяются на defaults. Размеры сохраняются прежними. Отдельного редактирования размеров в этой версии M2 нет; они загружаются seed. Новый товар создаётся с `sizes: []`. Это явная граница выбранного учебного контракта.

## M2, шаги 3–5. Фильтры, поиск и страницы

Промпт `m2_filters`, слайды140–142. Добавляйте и проверяйте параметры по одному, затем сочетайте их.

| Query к `/products` | ID |
|---|---|
| `brand_id=1` | 10,30 |
| `min_price=6000&max_price=8000` | 10 |
| `size=42` | 10,30 |
| `size=43` | [] |
| `search=nOrTh` | 10,30 |
| `brand_id=1&size=42&max_price=8000` | 10 |
| `brand_id=999` | [] |
| `search=%25` — буквальный знак `%` | [] |
| `limit=1&offset=0` | 10 |
| `limit=1&offset=1` | 20 |
| `limit=1&offset=99` | [] |

Все фильтры соединяются через AND. Границы цены включительны; `min_price > max_price` —422. Размер означает доступное наличие, то есть совпавший `size` **и** `stock > 0`. У размера43 есть строка, но stock0, поэтому карточка доступна по ID, а фильтр43 не находит совпадений.

```python
query = query.where(Product.sizes.any(
    (ProductSize.size == size) & (ProductSize.stock > 0)
))
```

`any` создаёт EXISTS и не размножает товар из-за нескольких размеров. Поиск использует `icontains(search.strip(), autoescape=True)`: без учёта регистра, символы `%` и `_` буквальные; пустой поиск не сужает список. Пользовательские значения передаются параметрами SQLAlchemy, а не вставляются в текст SQL.

`limit`: по умолчанию20, от1 до100; `offset`: по умолчанию0, неотрицательный. Сначала `ORDER BY Product.id`, затем LIMIT/OFFSET. Ответ — массив без total. При параллельном изменении каталога OFFSET не обещает неизменный состав страниц.

Отрицательные проверки: `limit=0`, `limit=101`, `offset=-1`, противоречивый диапазон цены, отрицательный размер и `min_price=NaN` →422. Пустая корректная выдача →200 с `[]`.

## M2, шаги 6–7. Сервисы записи и удаление

Промпты `m2_write` и `m2_delete`, слайды143–144. Подготовьте `create_product`, `update_product`, `delete_product`. Маршруты HTTP записи остаются закрыты до M3.

Commit/rollback принадлежат внешнему `transaction()` из unit_of_work.py. Сервис каталога получает его сессию, проверяет бренд и товар, делает flush и возвращает ProductRead до закрытия сессии. POST использует ProductWrite, PUT — ProductUpdate с версией. Авторизация завершает свою короткую сессию до начала бизнес-операции; на сессии с autobegin нельзя открывать второй обычный begin. Общие правила и пример составной операции приведены в разделе «Транзакции, сессии и устаревшие формы» README.

Политика удаления:

- Нет карточки →404.
- Нет ссылок корзины/заказов → удалить размеры и карточку одной транзакцией, HTTP204 без тела.
- На любой размер ссылается корзина или история → FK отклоняет удаление, rollback, HTTP409, исходные строки сохранены.

Проверка создаёт временный заказ501 на размер101, затем пытается удалить товар10. Ответ409 сопровождается неизменным снимком данных. Отдельно проверена ссылка **только из корзины** на размер301. После удаления временной ссылки товар30 удаляется вместе со своими размерами. Рабочий seed при этом не меняется: всё происходит в отдельной БД автопроверки.

Изменение текущей цены товара не изменяет `price_at_purchase` уже созданной исторической позиции. Ограничения FK не отключаются; каскадное удаление истории не добавлено.

## M3, шаг 1. Зависимости и локальный ключ

Остановите предыдущий Uvicorn через Ctrl+C, если он занимает8000. Установите закреплённые зависимости M3 и создайте ключ:

```sh
python -m pip install -r requirements-m3.txt
python -m pip check
python setup_jwt.py
```

`requirements-m3.txt` — полный закреплённый набор M0–M3, включая passlib1.7.4, bcrypt4.0.1 и python-jose3.5.0. Сочетание выполнено в этом учебном примере; состав стека соответствует заданию. M0–M2 по-прежнему могут использовать предыдущий `requirements.txt`.

`setup_jwt.py` создаёт случайный JWT_SECRET в существующем локальном `.env`, не печатает его и не заменяет заполненный ключ. Переменные окружения имеют приоритет над `.env`; не оставляйте случайно старую переменную в терминале. M3 при отсутствии ключа завершается ошибкой настройки. В коде нет общего запасного ключа.

```sh
python -m uvicorn app.store_main:app --reload --port 8000
```

JWT используется только в M3; запуск `app.main:app` и `app.catalog_main:app` не требует JWT_SECRET.

## M3, шаг 2. Регистрация

Промпт `m3_register`, слайд148. POST `/auth/register` принимает JSON:

```json
{"email":"anya@example.com","password":"Local-study-A7!"}
```

Это вымышленные данные локального упражнения. Ответ201 содержит только `id`, `email`, `is_admin:false`. ID берите из фактического ответа, не предполагайте7. Повтор нормализованного email →409; плохой email, короткий пароль и `is_admin:true` во входе →422.

Пароль8–72 символа, дополнительно максимум72 **байта UTF-8**, без NUL. Роль сервер задаёт False. Хэш хранится в `users.hashed_password`; `UserRead` его не содержит. Ошибки валидации не возвращают исходный пароль через `input`. Конфликт уникальности email обрабатывается с rollback — предварительный SELECT сам по себе не защищает от одновременной регистрации.

## M3, шаг 3. Проверить пароль и выдать JWT

Промпты `m3_hash` и `m3_login`, слайды149–150. [security.py](app/core/security.py) использует passlib и python-jose:

```python
saved = hash_password(password)
verify_password(password, saved)  # True
verify_password("wrong", saved)   # False
```

Сравнение с новым `hash_password(password)` неправильно: соль меняет строку. У несуществующего email проверяется dummy_hash; ответ401 такой же, как при неверном пароле. Это не гарантия абсолютно одинакового времени ответа.

POST `/auth/login` принимает **тот же JSON-формат**, а не OAuth2-форму. Успех:

```json
{"access_token":"<TOKEN>","token_type":"bearer"}
```

JWT: HS256, `sub=str(user.id)`, `exp` через15 минут, `iss=sneaker-practice`, `aud=sneaker-api`. Подпись проверяется с явным алгоритмом и обязательными claims. Пароля и роли в claims нет; payload читаемый, не зашифрованный. Ключ и токены не сохраняются в отчёте проверки.

## M3, шаг 4. get_current_user и Swagger

Промпт `m3_current`, слайд151. [dependencies.py](app/dependencies.py) выполняет:

1. Извлечение HTTPBearer.
2. Проверку подписи, срока, issuer, audience и обязательных claims.
3. Проверку формата/диапазона sub и поиск пользователя в БД.
4. Копирование пользователя в UserRead и закрытие сессии; при отсутствии пользователя — 401 с `WWW-Authenticate: Bearer`.

GET `/auth/me` возвращает `id`, `email`, `is_admin`. Не возвращает хэш. `require_admin` читает актуальную роль из этого снимка UserRead, а не из входного JSON.

В Swagger:

1. Вызовите `/auth/register`.
2. Вызовите `/auth/login`, скопируйте **значение** `access_token`.
3. Нажмите Authorize, в HTTPBearer вставьте токен **без** кавычек и слова Bearer.
4. Вызовите `/auth/me` и сравните email.
5. Выполните Logout в Authorize, повторите `/auth/me` →401.

Swagger добавляет `Authorization: Bearer …` самостоятельно. Для обычного HTTP-клиента заголовок нужно передать целиком. Logout очищает настройку Swagger, но не отзывает копии JWT на сервере. Публичный каталог после Logout продолжает читаться.

## M3, шаг 5. Назначить администратора локально

Промпт `m3_admin`, слайд153. Зарегистрируйте отдельный учебный `admin@example.com` обычным способом и получите его токен. До повышения роль False.

В другом терминале из того же корня и venv:

```sh
python -m app.promote_admin admin@example.com
```

CLI изменяет только явно выбранный существующий аккаунт в настроенной БД. Неизвестный email даёт отказ; автоматического создания с общим паролем нет. В публичной регистрации роли по-прежнему запрещены.

Тот же JWT теперь видит `is_admin:true`, потому что роль читается из БД на каждом запросе. Автопроверка также снимает роль в собственной временной БД и доказывает, что прежний JWT снова получает403 на запись.

## M3, шаг 6. Подключить защищённый CRUD

Промпт `m3_protect`, слайд154. Роутер [catalog_write.py](app/routers/catalog_write.py) использует зависимость `Depends(require_admin)` для всех трёх методов и повторную проверку роли под блокировкой в транзакции записи. GET подключены отдельно и публичны.

Для POST используйте полное тело карточки:

```json
{
  "name":"Practice Pair",
  "brand_id":1,
  "price":"8990.00",
  "description":"Lesson card",
  "image_url":null
}
```

Запомните выданные ID и version. Для PUT добавьте к телу `"version": 1` (фактическое значение из последнего GET этой карточки), измените эту отдельную карточку, затем удалите её. При 409 нужно перечитать карточку и заново внести изменения, а не повторять старое тело с новой версией. Не используйте в качестве успешного удаления товар с исторической ссылкой.

| Кто | POST | PUT | DELETE | Состояние БД |
|---|---|---|---|---|
| Без токена | 401 | 401 | 401 | Без изменений |
| Неверный токен | 401 | 401 | 401 | Без изменений |
| Обычный пользователь | 403 | 403 | 403 | Без изменений |
| Администратор | 201 | 200 | 204 | Подтверждённые изменения |

Используйте валидные тела и существующие ID, чтобы не спутать ошибки доступа с422/404. Для каждого отказа сравнивайте строки, а не только HTTP-код. DELETE204 имеет пустое тело. У администратора всё ещё действуют проверки ввода/ссылок:422 для неправильной цены,409 для неизвестного бренда или удаления товара со ссылками.

## M3, шаг 7. Отдельное ревью и воспроизводимая проверка

Промпт `m3_review`, слайд156. Ревью охватывает схемы, регистрацию, валидационные ошибки, security/config, get_current_user, require_admin, все три метода записи и CLI. Укажите команды и фактические результаты; пометьте невыполненные проверки отдельно.

Полный прогон готового эталона:

```sh
python verify_m23.py
```

Нужны работающий PostgreSQL и установленные `requirements-m3.txt`. Скрипт не требует постоянного JWT_SECRET: создаёт случайный ключ только для дочерних API-процессов. Не печатает ключ или токены.

Проверка создаёт новую БД `m23_check_<uuid>`, применяет миграцию и seed. Запускает настоящий Uvicorn сначала для M2, затем M3 на свободных локальных портах. Ни JWT, ни Depends, ни PostgreSQL не подменяются. CLI назначения администратора тоже выполняется настоящим отдельным процессом с адресом этой временной базы.

**85 проверок** покрывают:

- Закрытые методы записи на M2 и неизменность строк.
- Публичный каталог, форму ответа,12 наборов фильтров/страниц и отрицательные query-параметры.
- Регистрацию, нормализацию email, запрет роли во входе, отсутствие утечки пароля/хэша, UTF-8 ограничение bcrypt.
- Реальный login, `/auth/me`, подпись, срок, обязательные claims, неверный алгоритм, недопустимый sub и отсутствующего пользователя.
- Матрицу всех трёх методов записи, сравнение состояния после отказов, успешные POST/PUT/DELETE.
- Валидацию товара, неизвестный бренд/товар, сохранение истории и отдельную ссылку из корзины при DELETE.
- Сохранение исторической цены, удаление свободных размеров, повышение и отзыв роли с тем же JWT.

В `finally` завершаются дочерние Uvicorn-процессы, закрываются соединения и удаляется только созданная проверкой БД. Рабочие строки не очищаются. Сохранённый [m23-verification.json](m23-verification.json) содержит запросы, статусы, ID и результаты, без секретов. [m23-verified.js](m23-verified.js) передаёт эти данные автономной презентации.

Проверено на macOS/Python3.13.3/PostgreSQL17. Выполнение на Windows в этом окружении не проверялось. HTTP-проверка проверяет выдачу Swagger HTML и схему OpenAPI; она не выдаётся за автоматическое прохождение кнопок внешнего Swagger UI. Вёрстка и переключатели самой презентации проверяются отдельно.

После занятия остановите API через Ctrl+C и выполните `docker compose stop db`. Том остаётся для продолжения M4.

Источники: [SQLAlchemy SELECT/EXISTS](https://docs.sqlalchemy.org/en/20/orm/queryguide/select.html), [Pydantic Field](https://docs.pydantic.dev/latest/concepts/fields/), [FastAPI HTTPBearer](https://fastapi.tiangolo.com/reference/security/#fastapi.security.HTTPBearer), [Passlib bcrypt](https://passlib.readthedocs.io/en/stable/lib/passlib.hash.bcrypt.html).
