Примеры ниже рассчитаны на исходный seed; для независимого воспроизведения используйте проверочный скрипт с новой временной БД. Удалять рабочий том не требуется.

### Контракт корзины

| Запрос | Вход | Успех |
|---|---|---|
| `GET /cart` | JWT | 200, `{items, estimated_total}` |
| `POST /cart/items` | `product_size_id`, `quantity` | 200, новая или увеличенная позиция |
| `PATCH /cart/items/{item_id}` | `quantity` | 200, позиция с абсолютным количеством |
| `DELETE /cart/items/{item_id}` | JWT | 204 без тела |

Все четыре маршрута требуют входа. Владелец только из User, полученного по JWT. Входные схемы запрещают лишние поля. `quantity` и `product_size_id` — строгие int от1 до2147483647; `true`, дробь, строка вместо числа и0 дают422. Неизвестный размер404; чужая или отсутствующая позиция404. Превышение остатка409. Администратор в личном маршруте также ограничен своей корзиной.

Под токеном Ани:

```http
POST /cart/items
Content-Type: application/json

{"product_size_id":101,"quantity":1}
```

Пример формы ответа; `id` возьмите из своего запуска, не считайте его всегда равным1:

```json
{
  "id":1,
  "product_size_id":101,
  "product_id":10,
  "name":"North Runner",
  "size":"42.0",
  "price":"7990.00",
  "quantity":1,
  "stock":3,
  "subtotal":"7990.00"
}
```

Повторите тот же POST: id остаётся тем же, quantity2, subtotal15980.00. GET возвращает одну строку, estimated_total15980.00. Stock остаётся3. Затем POST quantity2 даст409: итог4 больше3; прежнее quantity2 сохраняется.

PATCH по **id корзины** с `{"quantity":1}` делает quantity1. DELETE по этому id даёт204 и пустое тело. Повторный DELETE404. Stock по-прежнему3: корзина не резервирует и не возвращает товар.

### Проверить два аккаунта

1. Аня добавляет размер101, сохраняет `id` CartItem.
2. Борис входит: его GET /cart возвращает свои строки либо пустой список.
3. Борис передаёт ID Ани в PATCH и DELETE с корректными входными значениями:404.
4. Аня снова читает корзину: quantity и строка прежние.
5. Повторите чужие PATCH/DELETE администратором: тоже404.
6. Без токена каждый из четырёх методов даёт401.

Для проверки администратора зарегистрируйте отдельный вымышленный `admin@example.com` и из терминала выполните:

```sh
python -m app.promote_admin admin@example.com
```

Публичная регистрация не принимает роль. Администратор нужен для статусов M5, а не для доступа к чужим корзинам.

### Одна транзакция и её владелец

```text
HTTP → JWT → auth Session читает User
                  │ копирует UserRead и закрывает auth Session
                  │ передаёт простой user.id
                  ▼
сервис открывает НОВУЮ Session + транзакцию READ COMMITTED
  1. User FOR UPDATE
  2. прочитать свою корзину
  3. ProductSize FOR UPDATE по возрастанию id
  4. Product FOR SHARE по возрастанию id: удержать цены
  5. проверить ВСЕ количества/остатки, посчитать Decimal total
  6. Order + flush → order.id
  7. OrderItem с ценой покупки + списание stock
  8. DELETE своей корзины
  9. собрать DTO в открытой Session
  выход из контекста → COMMIT → закрыть Session → вернуть201
  исключение        → ROLLBACK → закрыть Session → ошибка
```

Авторизация начинает чтение через autobegin, копирует UserRead и закрывает свою Session до вызова сервиса. Поэтому её соединение уже возвращено в пул, когда сервис получает id и открывает бизнес-сессию. На сессии с активной транзакцией нельзя вызывать второй обычный begin. Для составной операции внешний `transaction()` передаёт `session=db` в сервисы: они присоединяются к нему, а окончательный commit/rollback выполняет внешний владелец. `begin_nested()` — savepoint, а не замена завершению общей покупки. `flush()` отправляет SQL и даёт id; он **не** делает commit. Возврат DTO происходит после успешного выхода из контекста, сериализация не требует ленивых запросов к закрытой сессии.

Общий менеджер [unit_of_work.py](app/services/unit_of_work.py) задаёт локальные `lock_timeout=3s` и `statement_timeout=5s`. Известные отмены/конфликты SQLSTATE `40P01`, `40001`, `55P03`, `57014` переводятся после rollback в409 `concurrent_change_retry`. Прочие ошибки БД не маскируются. Автоматического повторения checkout нет.

Все операции корзины, включая GET, берут тот же User lock: это простой учебный способ согласовать корзину и checkout. Общий порядок уменьшает риск deadlock, но не обещает его отсутствия при взаимодействии с другими сервисами. Нельзя держать блокировки во время долгих внешних запросов; таких вызовов в этом сервисе нет.

### Успешный заказ вручную

На исходных данных добавьте Ане101 quantity2 и201 quantity1. Если в корзине уже есть101, POST прибавит количество — сначала проверьте GET, затем используйте PATCH абсолютного количества. Stock должны быть3 и5, цены7990.00 и5990.00. У Бориса оставьте отдельную строку301.

Выполните `POST /orders` без тела или с `{}`. `user_id`, `total`, цены и `_test_hook` в теле дадут422.

| Проверка | Ожидается |
|---|---|
| HTTP | 201 |
| status | created |
| total | `"21970.00"` |
| items | 2 позиции:101×2 и201×1 |
| price_at_purchase | `"7990.00"`, `"5990.00"` |
| Stock101 / Stock201 | 1 / 4 |
| Корзина Ани | пустая |
| Корзина Бориса | прежняя |

Пустая корзина →409 `empty_cart`. Недостаточный остаток →409 `insufficient_stock`. Если товара второй позиции недостаточно, первой позиции тоже нет в новом заказе: вся операция отклоняется. Общая сумма ограничена ёмкостью Numeric(12,2).

### История и статус

| Запрос | Доступ / поведение |
|---|---|
| `GET /orders?limit=20&offset=0` | Только свои, новые первыми; limit1..100, offset>=0 |
| `GET /orders/{order_id}` | Фильтр id AND user_id; чужой и неизвестный404 |
| `PATCH /orders/{order_id}/status` | Администратор; JSON `{"status":"processing"}` |

Оба GET личные и для администратора. Административный список всех заказов здесь не создаётся. История использует `price_at_purchase`, а не текущую цену Product. Снимок названия и картинки схема не хранит.

Уточнение учебного контракта статусов: `created → processing → completed`. Повтор текущего значения200 без эффекта. Пропуск или обратный ход409. Значение вне этих трёх —422. Без входа401, обычному пользователю403, неизвестный заказ404. В транзакции роль администратора повторно проверяется под FOR SHARE, Order блокируется FOR UPDATE. Изменяется только status; stock, позиции заказа и корзины не меняются.

### Двойной запрос и неизвестный исход

Два checkout одной корзины: первый держит User lock, оформляет и очищает; второй после ожидания видит пустую корзину и получает409. Если добавление началось после того, как checkout уже захватил User, оно ждёт и создаёт новую строку после покупки. При обратном порядке новая строка может войти в покупку.

Это **не полноценная идемпотентность**. Если соединение оборвалось после commit, клиент может не получить201 при реально созданном заказе. Не повторяйте оформление автоматически: сначала сверяйте историю. Надёжное повторение одного запроса с сохранением результата требует отдельного контракта `Idempotency-Key`, не реализованного в этой главе.

Для выполнения нужен запущенный учебный PostgreSQL и право учебного пользователя создавать/удалять БД. Рабочая `sneaker_shop` не очищается: проверка создаёт только свою `m45_check_<uuid>`, применяет миграцию и seed, запускает Uvicorn на свободном порту, закрывает сервер и удаляет временную БД в `finally`. JWT_SECRET генерируется только для тестового процесса; отчёт не сохраняет секреты.

[Проверочный код](verify_m45.py) создаёт [JSON-отчёт](m45-verification.json) и [JS-копию для слайдов](m45-verified.js). Интерактивные слайды показывают сохранённые результаты, не выполняют запросы к вашей базе. После локального прогона эти два файла обновятся только при полном успехе.

### Что действительно проверено

- **Настоящий HTTP:** регистрация/вход, восемь защищённых маршрутов, корзина, чужие ID, количество, отсутствие резерва, заказ21970.00, история, статусы, нехватка второй позиции, неизменность снимка при отказе.
- **Прямой вызов того же ORM-сервиса:** RuntimeError после flush Order, после первого списания, после удаления корзины до commit. В каждом случае совпадает полный снимок пяти таблиц. Это не HTTP-внедрение ошибки; внутренний callback не доступен клиенту. HTTP с `_test_hook` возвращает422.
- **Три настоящие HTTP-гонки:** последняя пара у двух покупателей; два checkout одной корзины; checkout и последующее добавление301. Отдельное соединение держит затвор на строке; два клиента действительно ждут блокировки, что видно в `pg_stat_activity` и `pg_blocking_pids`. Наблюдение очищает кэш статистики через `pg_stat_clear_snapshot`. Затем затвор отпускается, потоки завершаются, проверяются ответы и БД.
- **Таймаут:** удержание размера дольше3секунд даёт409 `concurrent_change_retry`, данные сохраняются.

| Гонка | HTTP | Состояние |
|---|---|---|
| Последняя пара | 201 + 409 | Один заказ, stock0, корзина проигравшего сохранена |
| Двойной checkout | 201 + 409 | Один заказ, своя корзина пуста |
| Checkout + добавление | 201 + 200 | Купленная корзина очищена; новая301 осталась |

Сравнение снимков исключает генераторы identity: пропуск номера после rollback допустим. Запуск двух запросов последовательно или задержка `sleep` без наблюдения не считаются доказательством конкуренции. Тест проверяет перечисленные сценарии, а не все возможные межпоточные расписания и не нагрузочную производительность.
