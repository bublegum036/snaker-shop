# Примеры SQLAlchemy Alembic и доступа для глав 7 и 8

Эти примеры сопровождают слайды 073–098 [презентации](../sneaker-backend.html). Они показывают ORM на настоящем PostgreSQL, две миграции, повторяемый seed, регистрацию, вход, JWT и проверку владельца заказа. После запуска можно проверить каждый механизм отдельно и объяснить, где запрос получает разрешение или отказ.

Это учебный стенд с семью таблицами и небольшим API. Каталог CRUD, оформление заказа и списание остатков здесь не реализованы. Все таблицы стенда находятся в отдельной схеме `lesson78_local`; для автоматической проверки создаётся отдельная временная схема. Данные предыдущего SQL-урока сохраняются.

## Поднять PostgreSQL

Используем Compose из предыдущей главы. Из корня репозитория:

```sh
cd presentation/sneaker-db-examples
```

Только если `.env` ещё не создан:

```sh
cp .env.example .env
```

Затем:

```sh
docker compose up -d --wait
docker compose ps
cd ../sneaker-orm-auth-examples
```

По умолчанию адрес с компьютера — `127.0.0.1:55432`, база — `sneaker_lesson`, роль — `lesson`, пароль — вымышленный `lesson-only`. Это локальный учебный стенд. Если в предыдущей главе изменили порт или реквизиты, согласуйте `DATABASE_URL` в `.env` этой папки перед подготовкой схемы. Для настройки нестандартного адреса можно скопировать шаблон вручную, заменить адрес и сгенерировать `JWT_SECRET`; существующий `.env` скрипт не перезаписывает.

## Установить зависимости

В папке `presentation/sneaker-orm-auth-examples`:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip check
```

Проверено на Python 3.13.3. `requirements.txt` фиксирует прямые и транзитивные зависимости проверенного окружения. Основные версии: SQLAlchemy 2.0.52, Alembic 1.20.0, psycopg 3.3.6, FastAPI 0.141.1, Pydantic 2.13.5, passlib 1.7.4, bcrypt 4.0.1, python-jose 3.5.0.

Сохраняем стек практического задания. Версия bcrypt зафиксирована вместе с Passlib по результату фактического запуска. Пароль проверяется на предел 72 байта UTF-8; тихого усечения нет. Версии учебного стенда не обозначают рекомендацию бессрочно использовать тот же набор в развёрнутом сервисе.

## Подготовить таблицы и данные

```sh
python prepare.py
python -m alembic current
python -m alembic history
```

`prepare.py` при первом запуске создаёт `.env` с новым случайным `JWT_SECRET`, затем отдельную схему, применяет миграции и запускает seed. Если `.env` существует, его значения сохраняются. Секрет не печатается и не входит в Git. `current` после успешной подготовки показывает `0002`.

Первая миграция создаёт семь таблиц без необязательного `products.image_url`. Вторая добавляет этот столбец. Это отдельная демонстрация эволюции схемы: после второй миграции набор полей соответствует текущим ORM-моделям. `metadata.create_all()` вместо миграций не используется.

Повторный seed:

```sh
python seed.py
```

Он вставляет недостающие учебные строки и оставляет существующие без изменения. Это не сброс базы и не восстановление исходных паролей, корзин или цен. Повтор проверяется по числу записей и неизменности существующего хэша. В миграциях хранится структура, в seed — конкретные значения.

## Запустить API и проверить доступ

```sh
python -m uvicorn run:app --host 127.0.0.1 --port 8007
```

Откройте [Swagger](http://127.0.0.1:8007/docs). Этот API использует порт 8007, чтобы не пересекаться с предыдущими примерами на 8000.

В стенде есть вымышленные учётные записи:

| Пользователь | Email | Учебный пароль | Роль |
|---|---|---|---|
| Аня, ID 7 | anya@example.com | Anya-demo-A7! | Покупатель |
| Борис, ID 8 | boris@example.com | Boris-demo-B8! | Покупатель |
| Администратор, ID 9 | admin@example.com | Admin-demo-C9! | Администратор |

Порядок проверки:

1. Вызовите `GET /auth/me` без токена. Ожидается `401`.
2. Выполните `POST /auth/login` с JSON `{"email":"anya@example.com","password":"Anya-demo-A7!"}`. Ожидается `200` с `access_token`.
3. В окне **Authorize** вставьте только значение `access_token`: Swagger сам добавит `Bearer` в заголовок.
4. Вызовите `GET /auth/me`. Ответ содержит ID 7 и email, без пароля и хэша.
5. Прочитайте `GET /orders/501`. Для Ани ожидается `200` и заказ с `user_id=7`.
6. Выполните вход Бориса, замените значение в Authorize его токеном и повторите `/orders/501`. Ожидается `404`. Запрос `/orders/999` даёт такой же ответ.
7. С токеном Ани вызовите `GET /admin/check`: `403`. С токеном администратора: `200`.
8. Попробуйте регистрацию с дополнительным `is_admin: true`: `422`. Обычная регистрация создаёт только покупателя. Повтор email даёт `409`.

`/admin/check` — вспомогательный маршрут урока для проверки прав, а не дополнительное требование к финальному магазину. `/auth/login` принимает JSON; здесь не используется OAuth2-форма. Заказ 501 и текущие корзины — независимые учебные состояния, как в предыдущей главе.

## Повторить автоматические проверки

```sh
python verify.py
python http_smoke.py
```

`verify.py` создаёт уникальную схему `lesson78_verify_…`, выполняет 38 проверок и удаляет только эту собственную временную схему в `finally`. Проверка не очищает `lesson78_local` и не требует, чтобы API был запущен отдельно. Ожидаемый итог:

```text
Verified 38 checks: migrations, ORM, hashing, JWT, API ownership and roles.
```

Проверяются:

- `upgrade 0001 → 0002`, `downgrade → 0001`, повторный upgrade и соответствие metadata;
- ошибка 42703 при новой модели и старой таблице;
- повтор seed без дубликатов и изменения существующего хэша;
- SELECT с результатом и без него, relationship, преобразование Decimal в JSON;
- ID после flush, невидимость вставки во втором соединении до commit, видимость после commit;
- откат после flush, восстановление Session после IntegrityError, автоматическое начало транзакции при SELECT;
- соль bcrypt, верный и неверный пароли, предел UTF-8, закрытое повышение роли через регистрацию;
- вход трёх пользователей, отсутствие/истечение токена, неверная подпись, обязательный exp, запрет другого алгоритма и отсутствие пользователя;
- роль из базы, снятие роли при старом токене, собственный/чужой/отсутствующий заказ и отсутствие хэша в публичном ответе.

FastAPI TestClient выполняет реальные зависимости и SQL-запросы. Авторизация не подменяется фиктивным пользователем. В проверенном окружении Starlette сообщает предупреждение о будущем отказе от httpx в TestClient; текущие проверки проходят. Это не ошибка приложения.

`http_smoke.py` дополнительно запускает настоящий Uvicorn на свободном локальном порту, проверяет `/docs`, OpenAPI, вход и защищённые ответы, затем останавливает только свой процесс. Для него сначала нужен `prepare.py` и неизменённые учебные данные `lesson78_local`. Сервер на 8007 можно оставить работающим: проверка использует другой порт.

`verification.json` и `verified.js` содержат результаты ORM и доступа; `http-verification.json` — статусы настоящего HTTP-запуска. Токены, секрет подписи и хэши в отчёты не записываются. HTML показывает сохранённые результаты и работает без запущенной базы. После повторной генерации отчёта перезагрузите HTML.

## Найти соответствующий код

| Файл | Что читать |
|---|---|
| `models.py` | Mapped, mapped_column, PK, FK и relationship |
| `database.py` | Engine, SessionLocal и отдельная схема PostgreSQL |
| `migrations/versions/0001_initial.py` | Самостоятельный снимок первой структуры |
| `migrations/versions/0002_image_url.py` | upgrade/downgrade для image_url |
| `migrations/env.py` | Подключение metadata и выполнение миграций |
| `seed.py` | Учебные записи и правило повторного запуска |
| `schemas.py` | Валидация входа и безопасные публичные ответы |
| `security.py` | bcrypt, выпуск JWT, проверка алгоритма и claims |
| `api.py` | get_current_user, require_admin, фильтр владельца |
| `verify.py` | Воспроизводимые положительные и отрицательные сценарии |

Команда `revision --autogenerate` со слайда 084 показывает, как создать следующую миграцию после изменения модели. В готовом стенде `0002` уже существует. Не создавайте дубликат без нового изменения. `downgrade` удаляет столбец вместе с данными; проверяйте откаты на одноразовой схеме, как делает `verify.py`.

## Что объяснить после урока

Почему присвоенный ID ещё не подтверждает commit? Почему изменение models.py не обновляет таблицу? Почему два хэша одного пароля отличаются? Почему прочитать payload не означает проверить токен? Почему валидный токен Бориса не открывает заказ Ани?

Пример показывает короткоживущий access token и серверную проверку роли/владельца. Refresh-токены, отзыв всех токенов при смене пароля, восстановление доступа и ограничение частоты входов — отдельные задачи полноценного приложения. Передача Bearer-токенов по внешней сети требует HTTPS. Здесь сервер запускается локально для урока.

## Остановить пример

Остановите Uvicorn сочетанием `Ctrl+C`. Базу можно остановить из папки предыдущего стенда:

```sh
cd ../sneaker-db-examples
docker compose stop db
```

Следующий запуск сохраняет данные тома. Удалять том для повторения урока не требуется.
