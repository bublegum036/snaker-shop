# Опыты оформления заказа и промпты для практики

Материалы для глав 9–10, слайды 099–120 [презентации](../sneaker-backend.html). Опыты показывают расчёт заказа, снимок цены, полный откат, лишнюю продажу при неверном алгоритме и реальное ожидание блокировок PostgreSQL. Полные промпты помогают повторять рабочий цикл с нейросетью: поставить небольшую задачу, прочитать diff, запустить, проверить и провести отдельное ревью.

## Что именно реализовано

`checkout.py` — небольшой синхронный опыт с psycopg и SQL. Это проверка механизма транзакции, а не готовый HTTP-модуль M5. Полную интеграцию с FastAPI, SQLAlchemy и зависимостями будем разбирать в практических главах. Пользователь в функции — уже установленный сервером внутренний `user_id`; эта функция сама не выполняет аутентификацию.

`verify.py` запускает 23 проверки на настоящем PostgreSQL, используя исходные семь таблиц и seed из главы 6. Для каждого независимого опыта создаётся новая схема `lesson910_<случайный идентификатор>`. В `finally` удаляется только эта созданная проверкой схема. Схемы прошлых уроков и пользовательские таблицы не очищаются. Проверка требует прав на создание схем в учебной базе.

## Поднять базу

Из корня репозитория:

```sh
cd presentation/sneaker-db-examples
```

Если `.env` ещё не существует, создайте его один раз:

```sh
cp .env.example .env
```

Затем:

```sh
docker compose up -d --wait
docker compose ps
cd ../sneaker-checkout-examples
```

По умолчанию используется вымышленная локальная учётная запись `lesson` с паролем `lesson-only`, база `sneaker_lesson` и адрес `127.0.0.1:55432`. Это тот же учебный сервис PostgreSQL из главы 5.

Если адрес или реквизиты отличаются, передайте `CHECKOUT_DATABASE_URL` через окружение. Ожидается URI вида `postgresql://…`, без суффикса `+psycopg`, который используется в SQLAlchemy. Скрипт не читает `.env` автоматически и не печатает строку подключения. Используйте именно учебную базу.

## Подготовить Python и запустить

В папке `presentation/sneaker-checkout-examples`:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip check
python verify.py
```

Проверено на Python 3.13.3 и psycopg 3.3.6. Если уже установили окружение предыдущей главы, из этой же папки можно выполнить без новой установки:

```sh
../sneaker-orm-auth-examples/.venv/bin/python verify.py
```

Ожидаемый итог:

```text
Verified 23 checkout checks, including real PostgreSQL lock waits.
```

Проверка выполняется без HTTP-сервера. Она не выдаёт статусы 201 или 409: возвращает результат внутренней операции либо отказ с причиной. Преобразование бизнес-ошибок в HTTP-ответы относится к будущему API. Пример `/health` в главе 10 — задание и критерии приёмки для M0, а не уже реализованный здесь маршрут.

## Проследить успешный заказ

Исходная корзина Ани, `user_id=7`:

| Размер ID | Товар | Цена одной пары | Количество | Исходный остаток |
|---|---|---|---|---|
| 101 | North Runner | 7990.00 | 2 | 3 |
| 201 | City Walk | 5990.00 | 1 | 5 |

Итог: `7990.00 × 2 + 5990.00 × 1 = 21970.00`. Цена возвращается из PostgreSQL как Decimal; float в расчёте не используется.

После commit создан один новый заказ со статусом `created`, две позиции с сохранёнными ценами, остатки равны 1 и 4, корзина Ани пустая. Корзина Бориса остаётся прежней. Исторический заказ 501 уже был в seed; новый заказ в свежем опыте получает ID 502. В другой базе номер может отличаться: проверять нужно сущность по возвращённому ID.

Затем отдельное изменение цены товара на 8990.00 подтверждает, что `price_at_purchase=7990.00` и итог уже созданного заказа не меняются.

## Проверить полный откат

В `checkout()` есть явно тестовый параметр `fail_at`. Проверка вызывает исключение в трёх точках:

1. После вставки `orders`.
2. После сохранения первой позиции и первого списания склада.
3. После удаления строк своей корзины.

Во всех случаях после rollback снимки `orders`, `order_items`, `product_sizes` и `cart_items` совпадают с исходными. Значения генераторов ID намеренно не сравниваются: PostgreSQL не обещает откатывать использованные номера последовательности.

Проверяются также пустая корзина, нулевой остаток, превышенное количество, нехватка второй позиции и запрет `quantity=0` на уровне БД.

## Сравнить два конкурентных алгоритма

Для каждого опыта создаются отдельные корзины: по одной паре размера 101 у Ани и Бориса, общий остаток — 1. Это другой исходный сценарий, а не продолжение успешной покупки двух позиций.

Намеренно неверный алгоритм расположен только в `verify.py`, функция `unsafe`. Два потока синхронизированы барьером после обычного SELECT: оба прочитали 1, затем каждый записывает вычисленное в памяти значение 0. В итоге созданы два новых заказа из одной пары. Ограничение `stock >= 0` не сработало, потому что отрицательного значения не возникло. Пример показывает конкретную потерю актуальности данных; не всякий способ UPDATE имеет такое поведение.

Корректный для показанного сценария алгоритм читает размер через `SELECT … FOR UPDATE` внутри транзакции. Второе соединение ждёт. Третье соединение наблюдает `pg_blocking_pids` и подтверждает, что ожидание действительно связано с первым участником. После commit первого второе читает остаток 0 и отказывает, сохраняя свою корзину. Результат — один новый заказ.

В опытах явно используется READ COMMITTED. При других уровнях изоляции возможны ошибки сериализации вместо того же пути выполнения. Таймауты конечны; тест не полагается на произвольную длительную паузу для воспроизведения гонки.

## Что защищает корзину одного пользователя

Для операций своей корзины выбран общий замок: `users` по ID текущего пользователя. Оформление и учебное добавление позиции сначала берут эту блокировку. Размеры затем блокируются в общем порядке ID; строки товаров читаются `FOR SHARE`, чтобы выбранные цены не менялись до конца покупки.

Два дополнительных опыта подтверждают:

- Второе оформление того же пользователя ждёт первое и затем видит пустую корзину. Создаётся один заказ.
- Добавление позиции ждёт завершения оформления и затем добавляет размер 301. Новая позиция остаётся в корзине после commit.

Протокол работает только если все пути изменения корзины его соблюдают. Произвольный SQL или маршрут, который его обходит, не получает эту гарантию. В полном приложении нужно согласовать также порядок блокировок с изменениями каталога и обработку deadlock/serialization failure. Проверенный код владеет транзакцией на свежем соединении с `autocommit=True`; его нельзя механически вставить после уже начатой транзакции SQLAlchemy.

Потеря ответа после успешного commit — отдельный вопрос. Повторный запрос здесь не обязан вернуть тот же заказ. Для такого контракта нужна отдельная политика идемпотентности с идентификатором операции и сохранённым результатом. Списание денег и отправка сообщений в этих опытах не выполняются.

## Прочитать и повторно создать результаты

`verification.json` содержит проверенные снимки, результаты ошибок и конкурентных опытов. `verified.js` — те же данные для автономного HTML. Повторный запуск `verify.py` обновляет оба файла. После него перезагрузите презентацию.

Переключатели слайдов 107 и 110 показывают сохранённые результаты. Они не подключаются к PostgreSQL из браузера. PDF показывает сравнительные таблицы, чтобы смысл сохранялся без интерактивности.

## Использовать промпты главы 10

В [prompts.json](prompts.json) находятся три полных шаблона:

| Ключ | Слайд | Назначение |
|---|---|---|
| `health` | 114 | Один шаг M0: реальное подключение через `/health`, ошибки и проверка восстановления |
| `debug` | 118 | Воспроизведение ошибки, факты, гипотеза и минимальное исправление |
| `review` | 119 | Отдельное ревью владельца ресурса и доступа двух аккаунтов |

В HTML нажмите «Открыть полный промпт», затем «Скопировать». Если браузер не разрешает доступ к буферу обмена, текст выделится и его можно скопировать `Ctrl+C` или `⌘C`. В PDF приведены короткие формы и разборы; полный текст доступен в этом комплекте и HTML.

Замените поля в угловых скобках и приложите актуальные файлы своего проекта. Реальные пароли, токены и ключи заменяйте маркерами. Промпты — материал для ученика, а не команда автоматически строить весь магазин во время подготовки презентации.

После ответа помощника прочитайте diff, выполните позитивный и относящийся к шагу негативный сценарий, проверьте состояние БД. Отдельно записывайте, что действительно запущено, а что ещё предстоит. Не принимайте статический `{status: ok}` вместо соединения или отсутствие фильтра владельца вместо защищённого маршрута.

Из папки `presentation/sneaker-db-examples`:

```sh

```
